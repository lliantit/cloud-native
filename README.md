# Лабораторна робота №2
## Дослідження моделей конкурентності та планування обчислень у Node.js та Go

**Дисципліна:** Cloud-native системи (Node/Go)  
**Виконав:** Михалюк Ілля

---

### Мета роботи
Дослідити відмінності в моделях конкурентності середовищ виконання Node.js (однопотоковий Event Loop) та Go (M:N планувальник, goroutines), порівняти їхню поведінку за асинхронного I/O та важких обчислювальних операцій (CPU-bound) під навантаженням.

---

### Опис реалізації

1. **Node.js (`node-api/server.js`)**:
    - `GET /io` - емуляція асинхронної I/O операції за допомогою `setTimeout(..., 2000)`. Не блокує Event Loop.
    - `GET /cpu` - важке синхронне обчислення (цикл на $5 \times 10^8$ ітерацій). Блокує основний потік виконання.

2. **Go (`go-api/main.go`)**:
    - `GET /io` - емуляція I/O операції за допомогою `time.Sleep(2 * time.Second)`. Виконується в окремій горутині, не блокуючи інші запити.
    - `GET /cpu-seq` - послідовне виконання двох важких обчислювальних циклів в одному потоці/горутині.
    - `GET /cpu-async` - конкурентне виконання обчислень шляхом розпаралелювання циклів у дві окремі горутини за допомогою `sync.WaitGroup`.

---

### Поведінковий аналіз (Ручне тестування блокування)

- **Node.js**:
  При відправці важкого запиту на `/cpu` і наступних запитів на `/health`, сервер **повністю перестає відповідати на `/health`**, доки не завершиться цикл у `/cpu`. Це демонструє головну особливість Node.js: тривалі синхронні CPU-операції блокують єдиний потік Event Loop, заморожуючи обслуговування всіх інших клієнтів.

- **Go**:
  При відправці запиту на `/cpu-seq` або `/cpu-async` сервер **миттєво відповідає на `/health`** з кодом 200 OK. Завдяки тому, що HTTP-сервер Go автоматично виділяє під кожен вхідний запит окрему горутину, а внутрішній планувальник (runtime scheduler) ефективно розподіляє їх між ядрами CPU, сервіс залишається чуйним навіть під час важких обчислень.

### Висновки

1. **Асинхронний I/O**:
   Обидві платформи показали ідентичну ефективність при операціях введення-виведення. При 10 одночасних клієнтах і фіксованій штучній затримці 2 с обидва сервіси стабільно видали очікувану пропускну здатність близько **5 RPS** без помилок (`http_req_failed = 0%`) з мінімальним споживанням пам'яті та процесорного часу.

2. **CPU-bound навантаження**:
    - **Node.js** продемонстрував значну деградацію швидкодії через блокування Event Loop. Запити шикувалися в чергу: перший оброблявся за ~400 мс, а наступні накопичували затримку аж до 12.18 с (`p95 = 11.10s`). Загальний RPS впав до **1.87**.
    - **Go** показав перевагу багатопотокової моделі з горутинами. Завдяки розпаралелюванню обчислень між доступними ядрами процесора через `sync.WaitGroup`, пропускна здатність склала **11.77 RPS** (у 6.3 раза вище, ніж у Node.js), а середній час відповіді склав лише **835.65 мс**.
